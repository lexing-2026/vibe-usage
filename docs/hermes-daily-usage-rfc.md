# Hermes 按调用时间统计用量（设计草案，尚未实现）

状态：调查与设计草案。按天统计、持久化账本、服务端迁移均尚未实现或发布。

## 已验证的问题

现有 `src/parsers/hermes.js` 读取 `sessions` 的累计 tokens，并将整个会话放入 `started_at` 所在的半小时桶。8 月 31 日开始、持续到 9 月 6 日的会话会一直更新 8 月 31 日的桶。将时间改成最后一条消息时间仍会把全部消耗集中在一天，不能恢复真实的日分布。

已在临时 SQLite fixture 中复现：连续 7 天各有 user/assistant 消息，累计输入 51,000,000、输出 1,000；解析器只生成 8 月 31 日的一个用量桶，而 session 的首尾时间正确跨到 9 月 6 日。此验证未修改用户数据库。

2026-09-07 对本地 Hermes 0.21.0（上游 commit `08b140d14e6c1d49f9b7ad02c9437fe940d54d65`）进行了只读验证：

- `sessions` 和 `session_model_usage` 都保存累计值，没有逐次调用用量表；样本中所有 `messages.token_count` 均为 NULL。
- `logs/agent.log` 的 `agent.conversation_loop: API call #…` 行有毫秒时间、会话标签、模型、输入、输出、可选缓存读取/写入、可选请求 ID。
- 两条调用分别为输入 18,585 / 输出 142、输入 30,198 / 输出 1,090，与数据库的输入 48,783 / 输出 1,232 完全对应。
- 上游的 output 已包含 reasoning。v0.10.22 先行修复了 reasoning 重复相加与 cache write 漏计，样本总量从错误的 50,437 修正为 50,015；这项修复不改变日期分配。
- 上游日志默认每份 5 MiB、3 份轮转备份，因此只读取当前日志不能长期提供完整历史。
- 服务端 ingest 对变小的桶有保护；删去客户端 state 也不会删除旧远端桶。直接切换到新日期会留下旧累计桶并造成重复。

源码依据：[用量记录](https://github.com/NousResearch/hermes-agent/blob/08b140d14e6c1d49f9b7ad02c9437fe940d54d65/agent/turn_usage.py)、[日志格式与轮转](https://github.com/NousResearch/hermes-agent/blob/08b140d14e6c1d49f9b7ad02c9437fe940d54d65/hermes_logging.py)、[数据库结构](https://github.com/NousResearch/hermes-agent/blob/08b140d14e6c1d49f9b7ad02c9437fe940d54d65/hermes_state_common.py)。

## 当前与拟议约束

当前：Hermes 解析器无持久化历史，以源数据库累计值生成完整快照；`state.json` 只保存成功上传项的哈希。上传和项目隐私仍由后端设置控制。

拟议：按真实调用日志生成时间桶，同时用独立、持久化的本地用量账本保留已读的调用，避免日志轮转后遗失历史。账本不是可随意删除的派生缓存，不放入 Codex cache 或上传 state。继续使用现有 bucket/session 键和后端隐私策略。

## 本地设计

1. 流式读取各 Hermes Home 的 `logs/agent.log` 与数字后缀轮转文件，每次只读到捕获的文件大小。只提取严格匹配的调用用量行；不采集聊天正文、错误堆栈、请求内容、认证信息、费用或账户资金来源。
2. 用现有会话标签和请求 ID 做本地关联及去重；请求 ID 缺失时使用会话、调用序号、原始时间和 token 字段的确定性指纹。身份在账本中哈希化；不新增上传身份字段。复制和轮转不能重复入账。
3. `in` 包含缓存读取/写入：从输入扣除 cache read，cache write 留在输入。日志 `out` 包含 reasoning，而日志没有每次 reasoning 拆分，所以按调用生成的桶保留这部分在 output 中，不再叠加数据库累计 reasoning，也不按比例臆测拆分。
4. 无时区的日志时间按源机器本地时区解释，首次归档后固定为 UTC。历史时区无法确认、计数不合法、读取失败或初始化时数据库与日志快照不一致，应提示并暂缓该来源，而不是生成不可靠快照。
5. 建议位置为 `~/.vibe-usage/ledger/hermes/`，采用版本化记录、原子写入和备份。去重索引与归档事实必须一并提交；写入失败不能推进读取位置。普通 sync/reset 保留账本，reset 仍只清上传状态。账本损坏时停止 Hermes 更新并提示恢复备份，不能悄悄从残余日志重建出较小总量。
6. 首次建账将保留日志的实际调用与数据库累计值核对。日志齐全的历史可以还原；缺失部分只能记录为沿用旧日期的历史余额，并明确提示无法分日。不得平均分摊，也不得把余额改记为安装日。后续日志只增加对应日期，历史余额不随轮转重新计算。

## 兼容与历史迁移

- 影响仓库：`vibe-usage` CLI/daemon、本地 ledger；`vibe-cafe` 的 Hermes 重建接口和来源格式状态；Mac/Windows 分发包需要包含同一版解析器。
- 新用户可在完整建账后使用新格式。既有 Hermes 用户先看到重建预览：旧桶、新桶、可还原时间范围、无法分日的余额、总量差异；确认前沿用旧格式。
- 建议新增显式的 `POST /api/usage/hermes/rebuild`：按已认证用户和已确认 hostname 限定范围，事务内备份并替换该设备的 Hermes buckets。保持 sessions 不变，拒绝其他 source；项目隐藏规则继续由后端执行。不能使用现有会删除同设备全部来源的 reset 代替。
- 重建时记录该用户/设备的 Hermes 格式版本。新 CLI 在现有 client metadata 中声明 `sourceFormats.hermes=2`；重建后旧格式 Hermes 上传单独拒收，其他来源照常接收，避免旧 daemon 再写回累计大桶。拒收原因须返回给新版 CLI，相关上传哈希不应提交。
- 重建要求全部新快照和备份准备完成后再提交。中断前后分别保持完整旧数据或完整新数据；不能先删再等待客户端逐批补齐。

## 发布顺序与回滚

1. 先部署后端的预览、事务重建及格式校验，保持旧客户端兼容，不自动迁移。
2. 再发布 CLI 并更新 daemon、Mac、Windows 使用的包；已有自动更新策略保持不变。
3. 经用户确认后逐设备重建；先用可完整核对的样本验证跨日分布、总量、重试、日志轮转、离线恢复以及旧进程仍运行的情况。
4. 回滚时暂停该设备的 Hermes 上传，在同一事务恢复备份和旧格式标记，再恢复旧解析器。保留新账本和备份以便重试；其他工具继续同步。

本提案触及 `AGENTS.md` 的来源权威性、持久化状态与 reset 语义、跨仓库 API 和迁移审批门槛。后续实施须遵循上述兼容、迁移和发布/回滚安排；这些部分不在 v0.10.22 的补丁修复范围内。
